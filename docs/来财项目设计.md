# 来财项目设计

「来财」用于组织联机传三。一场任务只集合、发车一次，同一批大号依次进入最多 45 个小号世界。大号和小号安装同一份 BetterGI 脚本 `js/来财/`，通过配置选择角色。本文记录四端职责、运行流程和验收状态。完整字段见[来财通信协议 v1](来财通信协议.md)，部署方法见[来财使用说明](../js/来财/README.md)。

| 端 | 负责的决定或动作 |
| --- | --- |
| A 服务端 | 管理房间和整场任务，决定当前世界、入场名单、路线放行、超时处置与结束。服务端保持单个 `server/server.js`。 |
| B 莫酱客户端 | 大号客户端把服务端授权转成具体游戏指令。小号侧只有一个主用户莫酱客户端，负责 BAT、两个 Windows 多用户的轮替及本地通信。 |
| C 来财 JS | 在本游戏会话内接单、执行、观察并回报。大号可执行指定路线、入场和退场。小号可切号、放行、观察成员及确认清场。执行一项指令后待命。 |
| D 管理端 | 创建、编辑和展示来财房间及参数，沿用现有房间管理流程。 |

## 1. 运行流程

### 1.1 集合与发车

1. 房间设置大号目标人数（1–3）、小号世界计划（最多 45 个 UID）、是否允许缺人继续跑，以及中途等待时限。“允许缺人继续跑”建议默认关闭。每个具体 Windows 多用户最多绑定 3 个小号 UID。
2. 每个大号以独立席位报名。小号侧主用户占一个席位，申报可承接的逻辑多用户及 UID。本机 BAT、安装目录、脚本通信目录和账号凭据由主用户或对应小号会话保管。
3. 配置的全部大号和主用户在线且就绪、计划 UID 有明确归属后，服务端发车并固定本场参数。首次集合始终满员。此时不要求小号池已经登录游戏。
4. 发车后，每个大号客户端为本场启动一次含「来财」的一条龙。各大号按本场约定在本地选择相同的内置路线包。包内容由来财版本控制，服务端只检查版本并协调执行序号。脚本启动后报告实际角色、版本和可接单状态。大号来财本次运行只注册一次 BetterGI 原版 `AutoPick`，脚本不内置拾取模板。

### 1.2 主用户调度两个多用户

“运行位置”是主用户可同时使用的两个位置，“多用户”是实际的 Windows 用户会话，“世界 UID”是该会话此次登录的小号。位置可以复用。例如多用户甲处理甲1、甲2、甲3，释放位置后可换成多用户丙。

| 时机 | 当前世界 | 主用户可以同时执行的动作 |
| --- | --- | --- |
| 首次准备 | 启动甲的 BAT，由甲的来财切到甲1并核验 UID | 启动乙的 BAT，准备乙1。乙1就绪后待命。 |
| 大号在甲1执行 | 甲保持甲1在线、观察成员 | 乙可继续准备。即使乙先就绪，也要等服务端授予开放权限。 |
| 甲1清场，服务端开放乙1 | 乙放行大号并保持乙1 | 主用户通知仍在运行的甲切到甲2。后续依次交替。 |
| 甲3清场，大号在乙3执行 | 乙保持乙3 | 甲名下小号已用完，主用户释放甲的位置，启动丙的 BAT，提前准备丙1。 |

服务端给出当前目标及待准备目标。主用户选择已有会话切号或启动目标 BAT。主用户负责观察启动过程，小号来财能执行后上报游戏可操作、切号和 UID 核验。连续两次清晰读到与目标逐位一致的本机 UID，并确认游戏可接人，才报告世界就绪。两个世界可以就绪，**只有服务端指定的当前世界可以放行大号**。

### 1.3 放行与确认进入正确世界

1. 服务端选定一个已就绪的世界，把本轮名单交给主用户。主用户让对应小号来财开放放行，等待名单已生效的回执。
2. 逐人授权申请。目标小号观察放行前的席位，大号确认从单人开始，只向指定 UID 申请。小号仅同意本次预期申请。
3. 大号报告转为 2P、3P 或 4P。目标小号在自己的队伍中连续观察到新增席位，并能将该行唯一对应到本次白名单成员。服务端将两端报告绑定到同一次世界尝试和大号席位，再确认入场。
4. 点击同意只记为已放行。重名、陌生访客、席位不一致、同时出现多处变化或 UI 识别不清时保持待确认，刷新复检直至到期。大号侧的团购房主名片识别不作为入场成功依据。

### 1.4 每条完整路线同步一次

1. 入场名单确定后，服务端授权第 1 条路线。每个大号客户端向本机来财派发“执行当前包第 1 条”，来财按本地配置定位路线。
2. 一条路线内部的传送、辅助追踪、战斗和拾取属于同一项指令。每席独立完成路线、确认抵达并稳定脱战后回报。持有本轮独立击败证据的席位回报 `success`，晚到且未获得个人击败证据的席位回报 `await-team`。服务端等所有有效席位完成，并取得本世界本条路线至少一份击败证据，才发下一条。
3. 例如三名大号正在跑第 2 条，甲和丙先完成，服务端显示 `2/3`。两人原地待命。乙也完成后，服务端先保存此次同步结果，再授权第 3 条。各客户端分别派发新的单条执行指令。
4. 最后一条成功时由来财随结果标记 `isLast`。所有有效席位完成最后一条后，服务端统一下达退出。如果所有有效席位均报告空包，记录原因并安排退场，该世界不计战斗成功。如果同一序号的末条标记相互矛盾，或部分席位报告空包而其他席位已有路线结果，服务端暂停派发、报告配置异常。限时内无法消除冲突时终止并退场。处理依据仅为实际回报，不上传路线清单、条数或摘要。

### 1.5 退场、轮换与结束

大号来财确认退回单人，小号来财确认 F2 队伍界面观测有效且稳定无人。清场覆盖所有可能已进入的大号，包括已超时降员者。服务端结束旧轮。主用户收到释放授权后，才能切走原小号或复用其位置。下一目标如果已准备好，服务端开放它。尚未就绪，大号留在单人状态等待。最后一个世界处理完毕或任务终止时，服务端记录每个 UID 的完成、部分完成、超时或跳过结果，通知收尾并释放房间。

## 2. 通信协议

### 2.1 通道及消息归属

跨设备复用莫酱现有的已登录 Socket 连接。大号客户端与本机来财使用独立的指令和事件通道。主用户为每个 Windows 多用户绑定可读写的来财目录，两个多用户分别接收自己的操作。客户端将单条指令在同一目录写完后改名交付。来财写完单条事件正文后再写对应的完成标记，客户端只消费已完成的事件。消息字段、回执及恢复规则见[来财通信协议 v1](来财通信协议.md)。

| 字段 | 使用范围 |
| --- | --- |
| `roomName`、`taskId` | 报名使用现有房间名。发车后以本场唯一标识关联所有运行消息。 |
| `messageId`、`replyTo` | 每条逻辑消息有唯一编号。重发沿用原编号，回执引用原消息。服务端放行与客户端派发给来财的指令分别编号，保留其关联。 |
| `worldUid`、`worldAttemptId` | 指定目标 UID 和此次准备、开放及执行的尝试。同一 UID 重试须能与上次区分。 |
| `seatId`、`rosterVersion` | 指定大号席位及当前有效名单版本。已接收的有效完成记录在名单缩减后保留。 |
| `workerId`、`slotId`、`slotGeneration` | 小号侧区分实际多用户、并发位置及本次占用。释放、换人后拒绝旧占用的回执。 |
| `routeSeq`、`isLast` | 路线序号从 1 开始。最后一条由来财标记。服务端按当前世界、席位和序号同步。 |

### 2.2 主要消息与完成条件

| 消息 | 方向 | 含义 |
| --- | --- | --- |
| `seat-ready` / `task-start` | B → A / A → B | 报名携带 `role` 和已安装的 `laicaiVersion`。A 按房间检查角色、人数和版本，全部席位就绪后发车。 |
| `executor-ready` / `heartbeat` | C → 对应 B → A，B 另报自身在线状态 | C 实际启动后回报角色、运行版本及可接单状态。小号 C 在对应多用户启动后才回报。心跳带当前动作及已知状态，B 在线与游戏执行端有响应分别记录。 |
| `prepare-world` / `worker-stage` / `world-ready` | A → 主用户 → 小号 C，结果原路返回 | 主用户启动或复用会话，小号准备指定 UID。进程创建、脚本接单、世界就绪分别报告。 |
| `open-admission` / `admission-opened` | A → 主用户 → 小号 C，确认原路返回 | 对应世界、名册和本轮开放权限已生效。 |
| `admit-seat` / `join-world` / `join-result` / `world-members` | A 经主用户通知小号 C，确认后经大号 B 通知该席申请，双方分别回报 | 小号确认本次席位已生效后，大号发申请。小号区分“已批准”和“实际在场”。服务端与大号观测对上后才授权下一席。 |
| `route-release` / `run-route` / `route-result` | A → 大号 B / B → 大号 C / C → B → A | 路线从 1 编号。按原序号回报独立成功、个人完成待队伍证据、空包、失败或取消。重复放行不会再次跑同一条。 |
| `roster-update` / `cancel-route` | A → B / 大号 B → C | A 通知本世界名单变更或终止。B 指定世界尝试、席位和序号，C 取消该次追踪并回报实际结果。 |
| `leave-world` / `seat-left` / `world-cleared` / `release-world` | A 经 B 通知退场，双方经 B 回报，A 授权主用户释放 | 退回单人、世界清空分别确认。最后授权释放原会话。 |
| `cancel-attempt` / `state-snapshot` / `task-end` | A ↔ B，B 向对应 C 转达本地动作 | 作废指定尝试、恢复当前任务状态、结束整场。主用户在准备超时时可先行撤销本地尝试，随即向 A 报告。 |

**收到、开始和完成需要分别表示。** 收到重复命令时返回已知状态。已完成者重发结果。关键状态落盘后再广播。发生断线时允许当前动作结束并缓存结果，随后停在待命点。重连后以服务端快照、客户端未确认事件和游戏现场对账。若战斗、启动 BAT 或切号已经发出却无从确认结果，先查现场，不能直接补跑或补报成功。

### 2.3 超时、独立 CT 与降员

| 情形 | 裁决与动作 |
| --- | --- |
| 初次席位未齐 | 保持等待，或按集合期限结束本次集合。缺员继续开关不用于首次发车。 |
| 多用户准备超时 | 主用户负责分段计时，服务端监督主用户及整次准备。建议初值为启动 90 秒、游戏可操作 180 秒、切号 180 秒、精确 UID 核验 30 秒，整次最多 6 分钟。明确失败立即处置，重复心跳不延长期限。 |
| 跳过一个多用户 | 保留该多用户已完成的 UID，当前 UID 记准备失败，名下其余未处理 UID 记连带跳过。撤销本次槽位代次，报告服务端并准备下一个可用候选。旧会话迟到的就绪回报失效。预备端失败不打断正在运行的世界。若故障进程不能安全释放，隔离该位置，健康位置仍可串行工作。 |
| 小号候选耗尽 | 尚有健康多用户及其未执行的 UID 时继续串行。已经没有可提供的世界时，在役世界正常收尾后结束整场，并列出未能执行的 UID。 |
| 大号入场、失联或路线超时 | 入场期限从小号已开放且本席获准申请时开始。路线命令接单等待和实际执行分别计时。已完成等待队友的大号不再计执行超时。多名大号同时进场失败，先复核小号 UID 和放行界面。 |
| 允许缺人继续跑 | 超时后由 A 将异常大号移出本世界有效名单，通知各端。剩余人数大于零、该路线成功结果已收齐，并已排除被移出者继续干扰后续战斗时，可放行后续路线。降员者先退出，最早在下一世界重新就绪。 |
| 禁止缺人继续跑 | 大号缺席超时后，A 停止整场推进，通知各端取消正在执行的路线并组织退场。此开关约束大号人数，小号准备失败仍按多用户跳过规则处理。 |
| 有效大号降为零 | 该世界不能判为成功。允许缺人的房间先安全收尾、限时等候下一世界的大号重新就绪，期限届满仍为零则结束整场。 |
| 路线取消 | 采用后续 BetterGI 为单次 `runFile` 提供的独立取消令牌（CT）。执行路线期间 B、C 保持控制消息可达。当前路线超时、该席被撤销或任务终止时，C 直接取消匹配调用的 CT，不能将取消排在本次追踪结束之后。已完成或序号不符的迟到取消不影响下一条。取消回执不计成功，退回单人和世界清空分别确认。 |
| 退场迟迟无法确认 | 小号仍可能有访客时保持当前账号，继续复核或隔离该位置。若状态无法安全恢复，任务中止并记录未确认的现场。释放房间记录不能授权切走未清场的小号。 |

## 3. ABCD 四端修改清单

### A 服务端

- 改动入口集中在 [server/server.js](../server/server.js)，保持单 JS 文件。
- 在房间模型、创建、编辑、查询及发车入口接入来财类型。复用登录、房权、在线状态和集合机制，给来财保留独立的长任务状态。团购原有的启动即结算、冷却与炸车规则不进入来财流程。
- 保存本场固定成员、参数和世界顺序，同时维护在役世界与预备世界，确保只有一个开放世界。处理逐人申请、双方入场回报、退场、清场与释放。
- 实现按完整路线序号的进度同步、末条收尾、限时与名单裁决。对参与人数为零、被撤销席位的迟到结果和服务重启分别处理。
- 持久化已确认的尝试、名单、路线进度、放行与截止时间，提供恢复快照及每个 UID 的最终结果。向房间广播当前/预备世界、席位进度与异常阶段。

### B 莫酱客户端

- 房间交互、席位状态及服务端消息接入 [client/index.html](../client/index.html)。本地 BAT 和文件通道由 [client/main.js](../client/main.js) 承接，通过 [client/preload.js](../client/preload.js) 暴露所需操作。
- 公共部分增加来财身份与配置、版本就绪、本地指令和事件收发、去重、未确认结果重传，以及重连后的现场核对。只向绑定的账号、任务、会话转发指令。
- 大号端每场启动一次来财，将授权落实为入场、执行第几条路线、取消指定路线或退场。界面分别显示运行、等队友、失败、已退场。
- 小号侧主用户维护白名单 BAT、Windows 多用户、各自的通信目录和 UID 映射。执行双位置轮替、阶段计时、整组跳过、新候选启动及故障隔离。已经就绪的预备会话保持不开门。
- 验证跨 Windows 用户的目录权限、独立输入和回执归属，支持不同安装路径。活动世界仍有大号时，另一位置失败不能关闭活动会话的 BetterGI 或游戏。

### C 来财 JS

- 使用一个 `js/来财/` 目录和一份脚本入口，配置选择大号或小号。共用接单、状态查询、结果回报、取消和待命逻辑。
- 大号角色在所选内置路线包中定位客户端指定的序号，执行完整路线，读取执行结果并报告 `isLast`。实现定向入场、观察自身席位、独立 CT 取消与退回单人。拾取固定使用 BetterGI 原版触发器。
- 小号角色接收单个 UID 的准备指令，登录或切号并准确核验。依令开放动态白名单，分别报告批准申请、实际在场、观察不明和可靠清场。清场后等待主用户的下一条指令，不自行遍历账号。
- 可从原传三 `AutoLocalLegendOneDragon` 迁移入场、路线、传送和原版拾取，从 `自动小号管理` 迁移切号、数字模板、申请放行与 F2 观测。团购脚本的重试、退场和伴随任务收尾可作参考。旧逻辑中的近似 UID、将点击批准记作入场、追踪异常仅写日志，都要改成明确的执行结果。

### D 管理端

- 改动入口为 [admin/admin.html](../admin/admin.html) 的房间管理界面。
- 在已有创建、编辑、列表、详情中增加来财房型，正确提交和回显该房型参数。管理端只做房型和配置适配。运行时调度、超时判断与同步授权由 A、B 承担。

## 4. 联调与验收顺序

| 顺序 | 场景 | 通过条件 |
| --- | --- | --- |
| 1 | 模拟执行端与虚拟时钟 | 初次缺席不能发车。两人先完成仍保持等待。允许/禁止缺人分别按配置处理。重复、迟到、跨账号或旧槽位回执不推进任务。 |
| 2 | 主用户和两个真实 Windows 会话 | 两端可以独立收发。大号在甲世界活动时，乙能独立截图、输入和预切，甲不受抢焦点、错目录或错误回收的影响。 |
| 3 | 一个大号、两个世界 | 准备、开放、申请、实际入场、逐条接单、退场、清场、换号完整闭环。大号即使在另一个世界显示 2P，目标小号没有观察到它时也不能确认入场。 |
| 4 | 三个大号、两条路线 | 第一条慢者未完成时无人执行第二条。撤销慢者后按房间配置继续或终止。匹配的独立 CT 被取消，旧取消不能中断新路线，JS 仍可接退场指令。 |
| 5 | 双多用户轮替、超时与恢复 | 甲1在役时乙1超时，甲继续，乙剩余 UID 按规则跳过，下一候选丙就绪也要等待开放。跨重连、重启及最多 45 个世界的任务，每个 UID 均有可区分的结果。 |

## 5. 分步修改计划

**实施状态**　步骤 1–8 的代码和模拟验收已通过独立审查。步骤 9 的常规回归、45 世界规模模拟和 Windows x64 桌面构建均已通过。真实游戏和跨设备实际操作尚待实机验收。各步依据及环境见第 6 节。

| 步骤 | 修改范围和工作内容 | 本步完成条件 |
| --- | --- | --- |
| 1　确定协议字段与状态转换（A、B、C） | 将第 2 节落实为四端共用的消息约定。逐项确定发件角色、必填字段、允许接收的阶段、回执、超时起点和终态。定义参与者与所属客户端的绑定、槽位代次、首次路线序号，以及房间状态与各人进度的展示字段。 | 用模拟消息走通一个世界的准备、入场、两条路线、退场和清场。重复消息、旧世界或旧任务的消息均不能推进当前任务。 |
| 2　接入房型和集合（A、B、D） | A 在单个 `server/server.js` 内接入建房、编辑、房间缓存、状态查询和发车。B 增加角色报名、参与开关、本机来财版本检查和任务占用。D 在现有房间界面录入、回显大号目标数、世界计划、缺人策略和时限。保留既有房间数据的默认行为。 | 1–3 名大号与 1 个主用户按配置满员才发车。主用户以莫酱身份占席，无需登录某个小号。拒绝重复 UID、超 45 个世界、同一多用户超 3 个 UID、版本不符及已关闭参与的席位。旧团购房仍能发车、结算。 |

| 6　打通进出世界的实机闭环（B、C，对接 A） | 小号按单席授权放行，区分“已批准”和“实际在场”。大号从单人向目标 UID 申请。两端分别报告，小号确认对应队员，大号确认自己进入 2P–4P。退场时分别报告大号回到单人及小号世界清空。 | 先用一个大号、两个世界打通进出，再补三大号逐席入场。进错世界、点击同意后未进入、重名、漏认及清场时仍有访客均不能误判成功。 |

| 8　接入超时、降员与恢复（A、B、C） | 接入小号阶段超时、大号入场/失联/路线超时，以及已完成席位等待队友的状态。按房间策略继续或终止。补齐撤销、清场隔离、每个 UID 的最终结果、重连快照和任务占用恢复。将来财纳入服务端既有定时重启处理。 | 用可推进的时钟和临时数据目录验证降员后保留已完成进度、零人不能成功、预备位置故障后单位置继续、候选耗尽后结束。在“已保存未发送”和“已执行未确认”两处断开并恢复，均不重复启动 BAT 或重跑路线。 |
| 9　端到端联调与回归（ABCD） | 先用模拟执行端覆盖 45 个世界，再按第 4 节进行双 Windows 会话和真实游戏联调。检查客户端正常安装入口能加载来财所需文件，管理端可回显房间配置，原团购仍通过回归。 | 自动化结果与实机记录分别列出。实机至少覆盖跨设备的主用户与大号、双会话同时截图与输入、三大号两条路线同步、追踪取消后的退场，以及预备端故障时当前世界继续。 |

**实施依赖**　步骤 1 完成后，步骤 2、3 的服务端工作与步骤 4 的本地通信可分别开展。步骤 3 可先用模拟报名和就绪消息开发，真实发车依赖步骤 2。步骤 5 和 7 可在步骤 4 之后分别开发。步骤 6 将调度、双多用户和游戏入场连起来。步骤 8 的故障用例随各步编写，最后用完整流程统一验收。

**步骤 7 的 BetterGI 接口约定**　采用 `feat/pathing-runfile-cancellation` 分支已给出的 JS 接口。来财为每次需要独立取消的 `pathingScript.runFile(path, cts.Token)` 调用新建 `CancellationTokenSource`，在 `finally` 中调用 `cts.Dispose()`。本地执行限时可用 `cts.CancelAfter(ms)`。外部取消由执行期间的回调调用 `cts.Cancel()`，等追踪收尾、Promise 返回后再回报。返回 `"canceled"` 时停止本条后续动作，返回 `"finished"` 时继续检查完整路线的完成条件。文件或执行异常会使 Promise 拒绝，全局停止优先并按全局停止处理。若取消发生在两个子追踪间，来财应在启动下一个调用前检查本条路线是否已撤销。

**验证范围**　协议、调度、超时、幂等、名单变化和持久化恢复可在本地模拟。游戏 UID 读取、真实在场名单、清场识别、后台 Windows 会话输入和实际战斗完成条件需要实机验收。现有团购测试只作为旧功能基线，来财的通过条件按上表单独记录。
